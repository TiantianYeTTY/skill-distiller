# 素材挖掘指南（三条证据线的具体挖法）

## 一、对话记录（transcript）挖掘

位置：`~/.workbuddy/projects/<项目路径编码>/<session-id>.jsonl`（会话超长被压缩时，压缩摘要也存于此）。

挖法：

1. 用户消息定位：搜 `<user_query>` 标签与 `"role":"user"`；上下文里有 `<command-name>` 的是斜杠命令调用，也是用户意图的一部分。
2. 重点收集四类发言：
   - **修正/否决**："不要 X""你写错 X""X 去掉"——每条都是一条硬规则候选；
   - **返工指令**：用户指出问题后 AI 重新做的那一轮——错误档案的直接素材；
   - **补充要求**："还要……""顺便把……"——流程步骤候选；
   - **情绪信号**：用户表达强烈不满的措辞——说明该规则权重最高，错误档案中保留原话。
3. AI 的自查发现（无用户反馈但确实修过的 bug）单独归档，标"自查"，不冒充用户反馈。

## 二、记忆日志挖掘

- `项目/.workbuddy/memory/YYYY-MM-DD.md`：当日工作流水账，含"用户定"条目、版本号演进、踩坑记录；
- `项目/.workbuddy/memory/MEMORY.md`：已蒸馏的长期约定，通常可直接进 SKILL.md 红线区；
- 用户级 `~/.workbuddy/user-*/MEMORY.md`：跨项目偏好（如 GitHub 账号、提交身份、开源规范），做"协作约定/开源规范"素材。

## 三、定稿交付物解析

原则：**看实际文件，不凭对话记忆**——对话中说过要改的未必真改了，以最终文件为准。

docx 类：

```bash
unzip -q 报告.docx -d /tmp/inspect && ls /tmp/inspect/word/
# 结构统计：段落/表格/图片/公式/页眉
grep -c "<w:p [^>]*>\|<w:p>" /tmp/inspect/word/document.xml
grep -c "<w:tbl>" /tmp/inspect/word/document.xml
ls /tmp/inspect/word/media/ | wc -l
grep -o "页眉文字" /tmp/inspect/word/header*.xml
# 样式：标题字号颜色、正文行距、引用块样式
grep -A6 'w:styleId="Heading1"' /tmp/inspect/word/styles.xml
```

注意：docx 文本提取要合并 `w:t` 与 `m:t`（公式文本），pandoc 生成的 OMML 减号是 U+2212，比对前先归一。

目录/代码类：逐层 `ls` + 读关键入口文件；脚本看头部注释与实际参数用法。

## 四、规则判定标准（硬规则 vs 协作约定）

进**硬规则**（违反即返工）：
- 用户明确否定过具体做法的（"不要横线""不要写 TXX"）；
- 导致过返工的；
- 用户重复强调 ≥2 次的；
- 用户用了强烈措辞的。

进**协作约定**：
- 沟通方式偏好（要点式汇报、一次只改一个点）；
- 目录与文件管理习惯（中间产物位置、归档方式）；
- 未造成返工但被纠正过一次的小事。

禁止收录：与定稿产出无关的闲聊偏好。

## 五、原始 Prompt 分诊

原始 Prompt 常见三类内容：

1. **仍有效的任务定义**（"分析试卷、统计考点、输出报告"）→ 融进 SKILL.md 目标与流程；
2. **与定稿冲突的结构**（如最初的多年级合一 12 部分结构，最终被七部分定稿取代）→ 在 methodology reference 中显式写"弃用说明"，不静默丢弃——这是给未来 AI 的决策依据；
3. **过时/重复的要求**（定稿中已体现得更细）→ 不再单独保留，避免规则打架。

判定基准：**定稿 > 用户后期修正 > 原始 Prompt**。

## 六、脚本收集

- 来源：项目 `.workbuddy/`（analysis/、output*/stage*/ 等）与交付目录；
- 只收**真实跑通过最终交付物**的脚本；实验废案（如被弃用的 PDF 管线）不收，但可在 reference 中一句话注明"曾尝试 X 路线已弃用，原因 Y"；
- 复制进 skill 前做两件事：
  1. 头部加**适配指南注释**——换场景（换年级/换课程/换模板）时必须改哪些数据结构、哪些参数；
  2. 确认无硬编码的会话级路径残留（有则改为参数或写明环境假设）。
